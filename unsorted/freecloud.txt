What is it?

Standard APIs and SDKs for apps to deploy server apps to a user-provided environment.

Why?


* get rid of app vendor lock (when developer of the app owns cloud and keeps user data)
* total privacy - server part of the app runs in user-owned isolated enviroment
* cost effiency - under-utilized server apps will cost nothing for each user
* same convenience for self-hosted and cloud provider options
* app developers can focus on making apps instead of managing infrastructure

Good use cases:

* federated networks apps (Matrix, ActivityPub)



Отличие от Coolify

Coolify позволяет запускать любые приложения в контейнерах, а также управляет разными СУБД (Postgres, MySQL).

BYOC фокусируется на приложения со сверх-низкой утилизацией (V8, WASM) и на стандартизированных интерфейсах хранения (SQL, Blob, KV).

Это дает большие гарантии безопасности, чем контейнеры. И позволяет запускать серверную часть для десятков и сотен приложений на самой худой виртуалке.

Tech spec

Components:

1. Compliant private cloud instance (PCI)
	* DNS zone
	* OAuth2 provider
	* Runtime and storage orchestrator
	* Storage options:
		* sqlite
		* blob storage (s3)
			* content-addressable storage (ipfs)
	* Connectivity:
		* http(s) endpoint (domain/path routing)
		* private app<>backend endpoint
		* http client
2. SDK is integrated to client apps and provides authenticated deployment to a PCI
	* obtains a token unique to a single instance of the client app
	* can query PCI for backend instances (servlets)
	* can deploy the "servlets"
	* servlets are identified by their hash, making them content-addressable.
	* can talk to backend if authorized by user


Example user flow:

Future consideration:
---

Private cloud has potential to become standard backbone for fediverse.
A single user cloud could take over all social networks: X, Instagram, YouTube, Patreon.
User can manage all their content within their own cloud (whenever its their server or just paid account - migration is allowed and endorsed).

There are multiple problems to solve:
* Spam (drop non-authentic or not welcome communication)
* DDoS attacks (avoid ActivityPub feed to be overwhelmed)
* highload

Another perspective is layered solutions that can integrate on various layers of the PCI:
* protect blog with a x402 paywal or captcha (reverse proxies)
* setup CDN-proxy for all your apps as another app (DNS management)
* backup (storage provider)


Monetizaion
---

Many users would like to monetize their space.
Monetization is about who pays and for what

For what is like:
* paid chat to the author
* access to content (single piece or subscription)

Who pays:
* user pays
* user pays for a group of user (family access)
* advertiser pays in exchange to show consumer ads along the content

This is not direct concert of BYOC, but the architecture should allow this use-case.

Example of such arch is:
* separate "Monetization" app with its own servlet
* non-invasive integration:
	* servlet gates access to a URL without interaction with underlying app
* invasive integration:
	* an app's servlet (e.g. blog) follows x402 protocol and return HTTP 402 when necessary, the "Monetization" app handles this response to enable users do the payment

Common services

Users may benefit from having some backends that are shared across servlets.

This could be, for example, data aggregation services like search engine. We should enable to declare dependency on such service, and that service may be shared with other apps.
THis however will lead to versioning problem. What if app A requires search engine v1, and app B requires search engine v2?
	- This might be solved by duck typing.
	- Or, instead of intriducing dependency, we should let search engine itself discover existing backend and dela with them the way they are.


Use cases:
 - RSS/ActivityPub/ATProto aggregation for social discovery/interaction
 - Search engine, sitemap builder
 - Analytics

Types of integration:
* aggregator looks into BYOC API and discovers all deployed resources, them access them giving available information
	- in this case, security is managed by apps - they may or may not let aggregator to access resources
	- maybe we should provide standard way to authorize apps between each other
* middleware injects into ingress, then manipulates requests/responses
	- this may be very useful if we want app to inject code or something like this
	- but it's hard to define approach that simple and secure in the same time
		- some bad actor can install middleware that steals data
		- in the same time it's hard to educate users on how they should manage middleware - they will simple install "Analytics for BYOC"
	- so probably, it's app to "blog app" to somehow let "analytics app" to integrate
		- or maybe it's "blog app" acts as search engine in previous example, it discovers "analytics app" in user's cloud and talks to it
